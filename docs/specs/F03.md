# Spec F03: the 48-hour auto-decline job

A booking request that has sat in `submitted` for 48 hours with no decision is declined automatically, which frees its day for someone else.

- **Sources:** `docs/requirements.md` (FR10, FR11, FR12, FR17), `docs/design/application-state-machine.md`, `docs/specs/F01.md`, `docs/specs/F02.md`, the author's feature rules and answers of 2026-10-13.
- **Rule numbers** (J1, R2, ...) are cited by the tests. Rules of other features are cited as "F01 L3", "F02 ST2" and so on.

## Out of scope

Setting up the scheduler on the hosting platform, telling anyone about an auto-decline, the 6-month removal (NFR7), deleting or erasing client data (F04).

## How the job runs

Decided by the author: a command run by an external scheduler.

| # | Rule |
|---|---|
| R1 | The job is the command `flask --app app auto-decline`. One run declines every overdue booking (J1) and then exits. It takes no arguments: given any, it changes nothing and exits with code 2, the usual code for a command used wrongly. |
| R2 | The command is meant to be run once an hour by a scheduler outside the application (cron, or a scheduled job on the hosting platform). `README.md` documents this with an example. The application itself contains no timer. |
| R3 | **Heartbeat.** A run that succeeds exits with code 0 and writes one line to the logger `app.jobs` at level INFO: "Auto-decline run: N declined.", where N is the number of bookings this run declined, which may be 0. The line is written on every successful run, so a log with no such line for over an hour means the scheduler is not running the job. The same line is printed on standard output. Like every log line of the application, the logged line goes to standard error (F01 E4). It contains no client details. |
| R4 | A run that fails exits with code 1 and changes nothing (J8). It writes one line to `app.jobs` at level ERROR, "Auto-decline run failed: <type of the error>.", and prints the same. As in F01 P1, the error's own message is never written, because database errors can quote client details. |
| R5 | **Last run.** Every successful run records the instant it ran, in the same all-or-nothing step as its declines: if the run cannot be recorded, nothing is declined either (J8). A failed run records nothing, so the last-run time goes stale when the job is failing or not being run. The recorded time never moves backwards: a run whose clock reads earlier than the recorded time leaves it as it is. |
| R6 | `GET /health` reports it: the response is `{"status": "ok", "auto_decline_last_run": <time>}`, where the time is the instant of the last successful run in UTC in the form `YYYY-MM-DDTHH:MM:SSZ`, or `null` if the job has never run successfully. If the last-run time cannot be read (the database is unreachable), `/health` still answers `200` with `auto_decline_last_run` as `null`. |
| R7 | `/health` never waits long for the database: it gives up reading the last-run time after 2 seconds, so a database that does not answer at all cannot hold the endpoint up. When the time cannot be read, one line is written to the logger `app.jobs` at level WARNING, "Last auto-decline run could not be read: <type of the error>.", so an unreadable database is not mistaken for a job that has never run. |

## What a run does

"Now" comes from the `CLOCK` of F01 and is an exact instant; all time here is elapsed time (F02 CK1, CK2).

| # | Rule |
|---|---|
| J1 | **Overdue.** A booking is overdue if it is in `submitted` and 48 hours or more have passed since it was first submitted. A booking at exactly 48 hours is overdue. The 48 hours never restart: a booking returned to `submitted` 47 hours after it was first submitted has 1 hour left, and one returned after 48 hours is overdue at once and is declined by the next run. This is deliberate. |
| J2 | **Declining.** A run moves every overdue booking to `declined`, marks it as auto-declined, and records the time of the change as now. |
| J3 | **Only `submitted`.** A run never changes a booking that is `contacted`, `accepted` or `declined`, however old it is. |
| J4 | **The day is freed.** Once a booking is auto-declined, a new public booking request for its day or days is accepted (F01 L3). |
| J5 | **Nobody is told.** A run writes nothing to `app.email`: no email to the client (FR17) and none to the management team. |
| J6 | **Final.** An auto-declined booking is declined like any other: no request can move it again (F02 ST2). |
| J7 | **Running again changes nothing.** A run made straight after another finds nothing overdue, declines nothing and reports 0. A booking is never declined twice: its time of change and its mark are those of the one run that declined it. |
| J8 | **All or nothing.** If a run stops part-way for any reason, no booking is left changed by it. The next run declines everything that is overdue. |
| J9 | **Two runs at once.** If two runs overlap, every overdue booking is declined exactly once (its row is changed once, not twice), and the numbers the two runs report add up to the number of bookings declined. |
| J10 | **Bookings being changed elsewhere.** A booking that another request holds at that moment (an admin's state change in progress) is skipped: the run does not wait for it and declines the rest. If that booking is still overdue afterwards, the next run declines it; if the admin moved it, it is left alone (J3). The other way round, an admin's state change that arrives while a run holds the booking waits for the run and is then refused as F02 R8, because the booking is declined. A booking never ends up both moved by the admin and auto-declined. |
| J11 | **No interference.** A run changes nothing about a booking except its state, its mark and its time of change, and nothing at all about bookings that are not overdue. Public booking requests and admin requests made during a run are answered as usual. |
| J12 | **Missed runs.** If no run happens for a while (the server was down for six hours), the first run afterwards declines everything that is overdue by then, in one go. The time of the change is the time of that run, not the 48-hour mark, so those days are freed late by the length of the gap. |
| J13 | **Elapsed time.** 48 hours is 48 hours of elapsed time whatever the clock face shows: the weekends count (FR12), and so do the nights the clocks change. |

## The mark

| # | Rule |
|---|---|
| M1 | Every booking carries a mark, auto-declined or not. It is set by J2 and by nothing else. A booking declined by an admin is not marked. |
| M2 | Every item of the admin list and every booking returned by a state change (F02 LI8, R7) gains the field `auto_declined`, a boolean: `true` for a booking the job declined, `false` for every other booking. |
| M3 | Auto-declined bookings stay in the admin list like every declined booking (F02 LI1). The `state` filter value `declined` lists both kinds. |
| M4 | On the admin page (F02 W3, W6), an auto-declined row shows "Auto-declined" in the State column in place of "Declined", and "Declined (final)" with no buttons under Actions. A booking declined by an admin shows "Declined", as before. The mark changes the label of a declined booking only. |

## Database

`bookings` gains the column `auto_declined`, a boolean that is false unless J2 sets it, and that can be true only when the state is `declined`. `docs/design/data-model.md` is updated with this feature.

A small table records when the job last ran successfully (R5).

`flask --app app init-db` adds the column to a `bookings` table that already exists, without changing any existing row's data, and creates the new table. This is the first change to an existing table; F01 said `init-db` "does nothing to tables that already exist", which now reads "never changes existing data". Accepted by the author as a v1 decision (Known limits).

## Known limits

- **Nothing in this repository schedules the job, and nothing raises an alarm.** If the scheduler is not set up on the server, no booking is ever auto-declined. The heartbeat line (R3) and the last-run time on `/health` (R6) make that visible to anyone who looks; watching them and alerting is left to the hosting platform. The schedule cannot be covered by the test suite; only the command can.
- **Schema changes are made by `init-db` altering the table in place.** A v1 decision for a single-node demonstration with no migration tool: there is no record of which changes have been applied and no way to undo one.
- **`/health` says `ok` even when the database is unreachable**; it then shows the last run as `null` (R6).
- **`/health` is open to anyone and reads the database on every call.** It tells a stranger when the job last ran, and each call opens a database connection; nothing limits how often it is called.
- **A booking is declined up to an hour late**, because the job runs hourly, and later still after an outage (J12).
- **A skipped booking waits for the next run** (J10), so it can be declined up to an hour later than the others.
- **Nobody is told about an auto-decline** (J5). The client holds a submission confirmation and hears nothing more.

## Where this differs from other documents

| Document says | F03 does |
|---|---|
| `application-state-machine.md`: the job "runs every hour" | The job is a command; running it every hour is the scheduler's part (R2). |
| F02 LI8: the list item has exactly ten fields | It gains an eleventh, `auto_declined` (M2). Two tracked F02 tests compare the whole item and must be changed by the author. |
| `skeleton.md`: `GET /health` returns `{"status": "ok"}` and does not need a database connection | It also returns `auto_decline_last_run`, read from the database (R6). The tracked skeleton test compares the whole body and must be changed by the author. |
| F01 Database: `init-db` "does nothing to tables that already exist" | It adds the new column to an existing table (Database). |

## Confirmed by the author

On 2026-10-13: the bounce-back rule in J1, the heartbeat and last-run time (R3, R5, R6), altering the table through `init-db`, not telling the management team (J5, matching decision 15 of `docs/reviews/R1.md`), and skipping bookings held by another request (J10).
