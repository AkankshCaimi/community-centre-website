# Spec F02: admin login and booking management

The management team's admin logs in, sees the booking requests, filters and searches them, and moves each one between states. A forgotten password can be reset with a token.

- **Sources:** `docs/requirements.md` (FR8, FR9, FR11, FR17, NFR1, NFR2), `docs/adr/0004-auth-session-cookies.md`, `docs/design/data-model.md`, `docs/design/application-state-machine.md`, `docs/specs/F01.md`, the author's feature rules and answers of 2026-10-13.
- **Rule numbers** (AU1, SE3, ...) are cited by the tests. Rules of F01 are cited as "F01 V5" and so on.

## Out of scope

Editing a booking's details (FR8; deferred, see below), deleting or erasing client data (FR18; that is F04), the 48-hour auto-decline job (FR12), the 6-month removal (NFR7), more than one admin account, pages for resetting a password, really sending email.

**Editing is deferred (v1 decision).** To move a booking to a new date, decline and re-request.

## API

All under `/api/v1/admin`. Every response is JSON with content type `application/json` (F01 S4).

| Endpoint | Needs a session | Does |
|---|---|---|
| `POST /login` | no | AU: starts a session |
| `POST /logout` | yes | SE5: ends the session |
| `GET /session` | yes | says who is logged in |
| `GET /bookings` | yes | LI: lists bookings |
| `PATCH /bookings/<id>/state` | yes | ST: changes a booking's state |
| `POST /password-reset` | no | PR1, PR2: asks for a reset token |
| `POST /password-reset/confirm` | no | PR3 to PR5: sets a new password |

### Responses

| # | Case | Status | Body |
|---|---|---|---|
| R1 | Logged in | `200` | `{"email": "<admin email>"}`, and the session cookie is set (SE1) |
| R2 | Wrong email or wrong password (AU2) | `401` | `{"error": "invalid_credentials"}` |
| R3 | No valid session on an endpoint that needs one (SE4) | `401` | `{"error": "not_authenticated"}` |
| R4 | Logged out | `200` | `{"status": "logged_out"}`, and the session cookie is cleared |
| R5 | `GET /session` with a valid session | `200` | `{"email": "<admin email>"}` |
| R6 | List of bookings | `200` | see LI7 |
| R7 | State changed, or already in that state (ST4) | `200` | the booking, in the form of LI8 |
| R8 | The booking is declined (ST2) | `409` | `{"error": "declined_is_final"}` |
| R9 | No booking with that ID | `404` | `{"error": "not_found"}` |
| R10 | Reset requested (PR1) | `200` | `{"status": "reset_requested"}` |
| R11 | Password changed (PR3) | `200` | `{"status": "password_changed"}` |
| R12 | Reset token not valid (PR4) | `400` | `{"error": "invalid_token"}` |
| R13 | A field or query parameter is refused | `400` | `{"error": "validation_failed", "fields": {"<name>": "<code>", ...}}` |
| R14 | Content type, body size or unreadable body, on `POST` and `PATCH` | `415`, `413`, `400` | as F01 A2, A3, A4 |
| R15 | Unknown address, wrong method, unexpected failure | `404`, `405`, `500` | as F01 A9, A10, A11 |

### Order of checks

**O2.** As in F01 V13, every refused field or query parameter is reported in the same response, one code each. For a value that breaks several rules, the first code listed in its rule is used.

**O1.** On an endpoint that needs a session, the session is checked first: without one the answer is R3 whatever else is wrong with the request. Then, in order: content type, body size and readability (R14), fields and query parameters (R13), whether the booking exists (R9), whether it is declined (R8). On the endpoints that need no session the order starts at R14.

## Reading the body

**B1.** Every `POST` and `PATCH` endpoint here follows F01 B1, B2 and B3: content type `application/json`, at most 64 KB, one readable JSON object. `POST /logout` therefore takes an empty object, `{}`. Fields not named in this spec are ignored.

## Login

| # | Rule |
|---|---|
| AU1 | `POST /login` takes `email` and `password`, both strings. The email is compared after trimming and ignoring letter case, by plain lower-casing with no language-specific rules; the password is compared exactly. If both match the admin account, a session is started (R1). |
| AU2 | A wrong email and a wrong password give the same response, R2, byte for byte, and set no cookie. |
| AU3 | Nothing happens on repeated failures: no lockout, no delay, no counter. After any number of failures the right email and password still log in. |
| AU4 | The password is stored only as an Argon2id hash. The password itself is never stored and never logged. |
| AU5 | `email` and `password` must each be a non-empty string; otherwise R13 with code `required`. `email` over 254 characters or `password` over 1024 characters: `too_long`. |
| AU6 | Each login attempt writes one line to the logger `app.auth` at level INFO: "Admin login succeeded." or "Admin login failed." Neither the email nor the password is logged (F01 P1). |
| AU7 | When the email is unknown, the same password-hashing work is still done, so the time taken does not reveal whether the email exists. |

## Sessions

"Now" comes from the `CLOCK` of F01.

| # | Rule |
|---|---|
| SE1 | A session is identified by a cookie named `admin_session` holding a random value of at least 32 bytes. The cookie is `HttpOnly`, `Secure`, `SameSite=Strict`, with path `/` and no expiry date of its own. |
| SE2 | The server stores only a SHA-256 hash of the cookie value, never the value. |
| SE3 | A session is valid while less than 30 minutes have passed since it was last used. Being used means any request that passes the session check; logging in counts as the first use. A request arriving exactly 30 minutes after the last use is refused. |
| SE4 | Every endpoint marked "needs a session" answers R3 when the cookie is missing, unknown, expired or logged out. |
| SE5 | `POST /logout` ends the session on the server (R4). The same cookie value never works again. |
| SE6 | Each login starts a new session with a new value. Earlier sessions are unaffected and stay valid until they expire or are logged out. |
| SE7 | There is no maximum total length for a session that stays in use. |
| SE8 | If a request carries more than one `admin_session` cookie, the first one is used and the others are ignored. |
| SE9 | `HEAD` on an endpoint whose method is `GET` is treated as that `GET` with no response body: it needs a session and counts as a use of it. |

## Time

| # | Rule |
|---|---|
| CK1 | Sessions, reset tokens and submission times are measured in elapsed time, not clock-face time. The hour repeated when the clocks go back is two separate hours: 30 minutes is 30 minutes there too. This also holds for the times stored by F01 (F01 S1). |
| CK2 | The `CLOCK` of F01 may return either a Europe/London local time without a time zone, as before, or a time carrying its own time zone, which is taken as that exact instant. The real clock returns the exact instant. A local time without a zone that falls in the repeated hour is taken as its first occurrence, so CK1 holds in that hour only for a clock that gives exact instants, as the real one does. |

## Response headers

| # | Rule |
|---|---|
| HD1 | Every response of the endpoints in the API table carries `Cache-Control: no-store`, so browsers and proxies keep no copy of bookings or of who is logged in. |

## Forged requests

| # | Rule |
|---|---|
| CS1 | The cookie's `SameSite=Strict` (SE1) keeps the browser from sending it on requests that come from other sites. |
| CS2 | Every endpoint that changes something is `POST` or `PATCH` and accepts only `application/json` (B1), which a form on another site cannot send. |

## The admin account

| # | Rule |
|---|---|
| CL1 | The one admin account is created by the command `flask --app app create-admin --email <email>`, documented in `README.md`. The password is typed twice at a hidden prompt and is never a command-line argument. |
| CL2 | The email must pass F01 V2 and is stored trimmed. The password must be 12 to 1024 characters with no control characters (as defined in F01). The two entries must match. |
| CL3 | On success the command prints "Admin account created." and exits with code 0. |
| CL4 | If an admin account already exists, or CL2 fails, the command creates nothing, prints the reason, and exits with code 1. |
| CL5 | `flask --app app init-db` (F01) also creates the tables this feature needs. |

## Password reset

| # | Rule |
|---|---|
| PR1 | `POST /password-reset` takes `email`, a non-empty string of at most 254 characters (otherwise R13: `required` or `too_long`). The response is always R10, whether or not the email belongs to the admin account. |
| PR2 | If the email is the admin's (compared as in AU1), a reset token of at least 32 random bytes is created, valid for 30 minutes, replacing any earlier token. Only its SHA-256 hash is stored. An email to the admin's address is written to the logger `app.email` at level INFO, like the emails of F01; it contains the admin's email as recipient and the token on a line of its own, in the form `Token: <token>`. If the email is not the admin's, no token is stored and nothing is written to `app.email` (see PR8 for what is done instead). |
| PR3 | `POST /password-reset/confirm` takes `token` and `password`. With a valid token the password is replaced (AU4), the token stops working, every session of the account is ended, and the response is R11. |
| PR4 | A token is valid if it matches the stored one, less than 30 minutes have passed since it was created, and it has not been used. Otherwise the response is R12 and the password is unchanged. A token arriving exactly 30 minutes after it was created is refused. |
| PR5 | `token` must be a non-empty string of at most 1024 characters (`required`, `too_long`). `password` must be a string of 12 to 1024 characters (`required`, `too_short`, `too_long`) with no control characters as defined in F01 (`invalid`). These are checked before the token (O1). |
| PR6 | If two requests use the same valid token at the same instant, exactly one is answered R11 and the other R12; the password is the one from the request that succeeded. |
| PR7 | The new password may be the same as the old one. |
| PR8 | **Same work either way.** `POST /password-reset` does the same work whether or not the email is the admin's, so the time it takes does not reveal which email is the admin's. In both cases a token is generated and hashed, the same single database statement runs and rewrites the admin's row, and exactly one line is written to the log: the email of PR2 if the address is the admin's, otherwise the line "Password reset requested for an address that is not the admin's." on the logger `app.auth` at level INFO. That line contains no email address. |

## Listing bookings

`GET /bookings` with optional query parameters.

| # | Rule |
|---|---|
| LI1 | **State filter.** `state` is one of `submitted`, `contacted`, `accepted`, `declined`; only bookings in that state are listed. Anything else: `invalid`. Without it, bookings in every state are listed, declined ones included. |
| LI2 | **Date filter.** `from` and `to` are calendar days in the form `YYYY-MM-DD`. Only bookings whose start, as a Europe/London date, is on or after `from` and on or before `to` are listed. Either may be given alone. Not a real date in that form: `invalid`. `to` earlier than `from`: `to` is `invalid`. |
| LI3 | **Search.** `search` is matched, ignoring letter case, against any part of the name, email or phone as stored. It is trimmed first; empty means no search. Over 100 characters: `too_long`. Containing a control character (as defined in F01): `invalid`. The characters `%`, `_` and `\` in it are ordinary characters, not wildcards. |
| LI4 | **Sort.** `sort` is `submitted_at` (the default), `starts_at` or `name`; anything else: `invalid`. `order` is `desc` (the default) or `asc`; anything else: `invalid`. The default is therefore newest submitted first. `name` sorts ignoring letter case. Bookings equal on the sort value are ordered by ID in the same direction. |
| LI5 | **Pages.** `page` is a whole number from 1 (default 1). `page_size` is a whole number from 1 to 100 (default 20). Not a whole number in ASCII digits: `invalid`. Outside the range: `out_of_range`. A number written with more than 100 digits, leading zeros included, is also `out_of_range`. A page past the end is an empty list, not an error. |
| LI6 | Filters and search combine: a booking is listed only if it passes all of them. Query parameters not named here are ignored. If a parameter is given more than once, its first value is used. |
| LI7 | The response is `{"items": [...], "page": <page>, "page_size": <page_size>, "total": <number of bookings passing the filters and search>}`. |
| LI8 | Each item is `{"id", "state", "name", "email", "phone", "guest_count", "starts_at", "ends_at", "details", "submitted_at"}`. The three times are Europe/London local times in the form of F01 V5. `details` is `null` when the client gave none. Text is exactly as stored (F01 S2); the client's network address is not included. |

## Changing a booking's state

`PATCH /bookings/<id>/state` with `state` and, for a decline, `confirm`.

| # | Rule |
|---|---|
| ST1 | `state` must be one of `submitted`, `contacted`, `accepted`, `declined`. Missing or not a string: `required`. Any other value: `invalid`. |
| ST2 | **Declined is final.** If the booking is declined, every request is refused with R8 and nothing changes, whatever `state` it asks for. |
| ST3 | From `submitted`, `contacted` or `accepted`, a move to any of the four states is allowed, backwards moves included. |
| ST4 | A move to the state the booking is already in changes nothing and has no side effects; the response is R7. |
| ST5 | A move to `declined` needs `"confirm": true`. Without it, or with any other value: R13 with `confirm`: `required`. `confirm` is ignored for the other states. |
| ST6 | A change of state records the time of the change. |
| ST7 | **Accepting.** A move into `accepted` from another state writes a confirmation email to the client to the logger `app.email` at level INFO, containing the recipient (the client's email), the client's name, and the start and end in the form of F01 V5. Line breaks in client text are collapsed (F01 P1). Each such move writes one email, so a booking accepted twice gets two. |
| ST8 | **Declining.** A move into `declined` frees the booking's day or days: a new public booking request for them is accepted (F01 L3). Nothing is written to `app.email` (FR17). |
| ST9 | Moves into `submitted` or `contacted` write nothing to `app.email`. |
| ST10 | `<id>` that is not a whole number, or that matches no booking: R9. |
| ST11 | **Simultaneous requests.** ST2 holds when requests arrive at the same instant: once a decline has been answered with R7, no other request leaves the booking in another state, and a decline and an accept sent together always end with the booking declined. |

## Admin page (React)

At the address `/admin`. The public form of F01 stays at `/`.

| # | Rule |
|---|---|
| W1 | On opening, the page asks `GET /session`. With a session it shows the bookings; without one (R3) it shows the login form. |
| W2 | The login form has inputs labelled "Email" and "Password" (a password input) and a button "Log in". It sends `POST /login` as JSON. On R1 it shows the bookings. On R2 it shows "The email or password is not correct." On anything else, "Something went wrong. Please try again later." |
| W3 | The bookings view has a table with the columns Name, Email, Phone, Guests, Start, End, State, Submitted, Details and Actions, one row per item of the list. Times are shown as `YYYY-MM-DD HH:MM`. The State column shows Submitted, Contacted, Accepted or Declined. With no items it shows "No bookings found." |
| W4 | Above the table: a "State" select (All, Submitted, Contacted, Accepted, Declined), date inputs "From" and "To", a "Search" box, a "Sort by" select (Submitted, Start, Name), an "Order" select (Newest first, Oldest first), and a button "Apply". Pressing Apply requests the list with those values as the query parameters of LI1 to LI4, leaving out the empty ones, and goes back to page 1. |
| W5 | Below the table: "Page X of Y" and buttons "Previous" and "Next", disabled on the first and last page. They request the neighbouring page with the same filters. |
| W6 | In the Actions column a row has one button for each state other than its own: "Mark submitted", "Mark contacted", "Accept", "Decline". A declined row has no buttons and shows "Declined (final)". |
| W7 | "Mark submitted", "Mark contacted" and "Accept" send the `PATCH` at once. "Decline" first opens a dialog "Decline this booking? This cannot be undone." with buttons "Yes, decline" and "Cancel". Only "Yes, decline" sends the `PATCH`, with `"confirm": true`; "Cancel" sends nothing. |
| W8 | After a successful change the row shows the new state and its new buttons. On R8 the page shows "This booking is declined and cannot be changed." and reloads the list. On any other failure it shows "Something went wrong. Please try again later." |
| W9 | A button "Log out" sends `POST /logout` and returns to the login form. |
| W10 | If any request is answered with R3, the page returns to the login form and shows "Your session has ended. Please log in again." |
| W11 | All client text (name, email, phone, details) is shown as text. Markup in it is never interpreted (F01 S4). |
| W12 | **The decline dialog of W7 is shown where the admin is looking.** It is drawn over the page, fixed to the window, so it is in view whatever the scroll position, never added to the end of the page. While it is open: focus moves to its "Cancel" button when it opens; Tab and Shift+Tab move only between its two buttons; Escape closes it as "Cancel" does and sends nothing. When it is closed by "Cancel" or Escape, focus returns to the "Decline" button of the row it was opened from. |

W12 was added on 2026-10-23. On the live site the dialog opened below the table, the pagination and "Delete client data", out of view: "Decline" seemed to do nothing, and no booking could be declined. W7 had said what the dialog contains but not where it appears, and tests in a browser without a screen could not tell the difference.

## Settings

None new. The admin account is created by the command of CL1, not by a setting.

## Database

Two tables are added to `backend/db/schema.sql`, as in `docs/design/data-model.md`: `admin_users` (with the Argon2id hash and the reset-token columns) and `admin_sessions` (one row per session, holding the hash of the cookie value and the time of last use). Access stays plain SQL through the repositories.

## Known limits

Accepted by the author on 2026-10-13.

- **The reset token is written to the log**, because emails are logged, not sent (PR2). Anyone who can read the log within 30 minutes can take over the admin account. While sending is stubbed the log is the inbox; the token never appears in logs once real email sending lands.
- **No limit on login attempts** (AU3, from NFR1) and none on reset requests: passwords can be guessed without restriction, and each reset request writes another email to the log.
- **No pages for resetting a password.** The admin takes the token from the log and calls the API.
- **The server cannot stop a client from sending the session cookie over plain HTTP**; the `Secure` attribute relies on the browser.
- **Bookings cannot be edited.** To move a booking to a new date, decline and re-request. Declined is final, so the client has to submit a new request.
- **Delete is not in F02**, although FR18 lists it for the admin page; it is F04.

- **Reset requests can block a reset.** Each request replaces the token (PR2), so someone who knows the admin's email can keep the admin's own token invalid by asking repeatedly.
- **The admin page can be framed.** Nothing in the application stops another site showing the admin page inside a frame; whatever serves the page must forbid it.
- **Search terms travel in the address.** A client's name, email or phone typed into the search box appears in the request address (LI3), so it reaches the access logs of the server and any proxy.
- **Very long cookies and addresses are left to the web server.** The application sets no limit of its own.
- **A server clock corrected backwards** can keep a session or token alive for longer than 30 minutes.

## Where this differs from other documents

Decided by the author on 2026-10-13. `requirements.md` has not been changed.

| Document says | F02 does |
|---|---|
| FR11: a fixed list of allowed moves; accepted can go back to contacted only | Any move except out of declined (ST3), as already recorded in `application-state-machine.md`. |
| FR8: options to edit or cancel booking requests | State changes only; "cancel" is a move to declined. Editing is deferred: to move a booking to a new date, decline and re-request. |
| NFR5: log files hold no personal data | ST7 writes the client's name and email, and PR2 the admin's email and the reset token, to the application log, in the same way as the emails of F01, until real sending exists. Nothing else personal is logged (AU6). |
| `data-model.md`: admin sessions "not in this model" | A new `admin_sessions` table. `data-model.md` is updated with this feature. |
| `application-state-machine.md`: a booking moved back to `submitted` after 48 hours is auto-declined | The auto-decline job does not exist yet, so nothing happens. |

## Decided as default conventions

On 2026-10-13 the author asked for default conventions on the points the hostile-input review found the spec silent on. These rules are the implementer's choice of convention under that instruction: CK1, CK2, HD1, SE8, SE9, PR6, PR7, the control-character rules in LI3, CL2 and PR5, the 100-digit limit in LI5, the first-value rule in LI6, the precedence rule O2, the lower-casing rule in AU1, and the five Known limits from "Reset requests can block a reset" to "A server clock corrected backwards". PR8 was added on the author's instruction of 2026-10-13 that reset requests must not leak the admin's email through timing.

## Proposed by the implementer, approved by the author

All of the following were approved by the author on 2026-10-13.

- The endpoint addresses other than `/login`, `/bookings` and `/bookings/<id>/state`, and every response body and error name in the responses table.
- `POST /logout` taking an empty JSON object (B1).
- Missing or empty login fields answered with `400` (AU5), not `401`.
- The login log lines of AU6 and the timing rule AU7. AU7 has no test: it cannot be checked from outside without measuring time.
- Storing only hashes of the session value and the reset token (SE2, PR2); the cookie's name and its `Secure`, `SameSite=Strict` and no-expiry attributes (SE1).
- Exactly 30 minutes counting as expired (SE3, PR4); no maximum session length (SE7); several sessions at once (SE6).
- The command's name, its hidden prompt, and the 12 to 1024 character password rule (CL1 to CL4, PR5).
- A reset token lasting 30 minutes, a new request replacing the old token, and a reset ending every session (PR2, PR3).
- The date filter applying to the booking's start, as London days (LI2), and `to` before `from` being an error.
- The three sort fields, the tie-break by ID, page size 20 with a maximum of 100, search limited to 100 characters (LI3 to LI5).
- The list item's fields, and leaving out the network address (LI8).
- A request to move a booking to its current state answered as success with no side effects (ST4); any request on a declined booking refused, including declined to declined (ST2).
- An email on every move into accepted, including a second acceptance (ST7).
- The admin page's address, columns, labels, time format and every message (W1 to W10).
