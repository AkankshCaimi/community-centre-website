# Spec F04: deleting client data, the retention purge, and the terms and privacy notice

An admin can delete a client's data on request. A scheduled job deletes it anyway six months after the request was submitted. The booking form links to real terms and a real privacy notice.

- **Sources:** `docs/requirements.md` (FR5, FR18, NFR4, NFR7), `docs/reviews/R1.md` (decisions 20 to 25 and the UK GDPR facts), `docs/design/data-model.md` (Erasure), `docs/specs/F01.md`, `F02.md`, `F03.md`, the author's feature rules and answers of 2026-10-13.
- **Rule numbers** (E1, D2, ...) are cited by the tests. Rules of other features are cited as "F02 SE4", "F03 R6" and so on.

## Out of scope

Removing client details already written to the application log, backups (there are none, NFR8), recording which version of the terms a client agreed to, really sending email, a client deleting their own data.

## What erasing a booking means

| # | Rule |
|---|---|
| E1 | Erasing a booking empties its client details and keeps the row. **Emptied:** name, email, phone, network address, guest count, details, and the two tick times. **Kept:** ID, state, the auto-declined mark, start and end, submission time, time of the last state change. The time of the erasure is recorded. |
| E2 | Erasing is permanent. Nothing brings the details back. |
| E3 | An erased booking that is not declined still locks its day (F01 L3). |
| E4 | An erased booking no longer counts towards anyone's slot limit (F01 L2) or any network address's rate limit (F01 L1). |
| E5 | A booking is erased at most once: its time of erasure is that of the first erasure, whoever or whatever did it. |

## Deleting by an admin

A client asks by phone or email; the admin carries it out. `POST /api/v1/admin/bookings/<id>/erase` with `{"confirm": true}`.

| # | Rule |
|---|---|
| D1 | The endpoint needs a session (F02 SE4, O1), accepts only a JSON object (F02 B1), and answers with `Cache-Control: no-store` (F02 HD1). |
| D2 | `confirm` must be the JSON value `true`. Otherwise: `400`, `{"error": "validation_failed", "fields": {"confirm": "required"}}`. |
| D3 | `<id>` that is not a whole number, or matches no booking: `404`, `{"error": "not_found"}` (as F02 ST10). |
| D4 | **Only when the booking is no longer live.** A booking can be erased if it is declined, or if its end is not later than now. Otherwise: `409`, `{"error": "booking_is_live"}`, and nothing changes. To delete the data of an upcoming booking, the admin declines it first. |
| D5 | On success the booking is erased (E1) and the response is `200` with the booking in the form of F02 LI8 and F03 M2, its `name`, `email`, `phone`, `guest_count` and `details` being `null`. |
| D6 | **Deleting twice.** Erasing a booking that is already erased, by an admin or by the purge, answers `200` with the same body and changes nothing (E5). This holds whatever its state and dates, so D4 is not checked for an erased booking. |
| D7 | **Two admins at once.** If two requests erase the same booking at the same instant, both answer `200` and the booking is erased once (E5). |
| D8 | Each erasure by an admin writes one line to the logger `app.auth` at level INFO: "Booking <id> erased by an admin." A repeated request (D6) writes nothing. The line holds no client details. |
| D9 | The checks run in this order: session, body, `confirm`, whether the booking exists, whether it is already erased (D6), whether it is live (D4). |

## Erased bookings in the admin API

| # | Rule |
|---|---|
| A1 | An erased booking stays in the admin list (F02 LI1 to LI7). Its item has `null` for `name`, `email`, `phone`, `guest_count` and `details`; `id`, `state`, `starts_at`, `ends_at`, `submitted_at` and `auto_declined` are as before. No field is added: a `null` name means the booking is erased, since every other booking has a name. |
| A2 | `search` never matches an erased booking. The state and date filters apply to it as to any booking. With `sort=name`, erased bookings come after every named booking in ascending order and before them in descending order. |
| A3 | The state of an erased booking can still be changed (F02 ST1 to ST11), so that an erased booking can be declined to free its day. A move into `accepted` writes no email for an erased booking, as there is no one to send it to (F02 ST7). |
| A4 | The auto-decline job treats an erased booking like any other (F03 J1 to J3). |

## The purge job

A scheduled job like F03's.

| # | Rule |
|---|---|
| P1 | The job is the command `flask --app app purge`, run once an hour by the same outside scheduler as F03's job (F03 R2). It takes no arguments: given any, it changes nothing and exits with code 2. |
| P2 | **Retention.** A booking is due if it is not erased and six calendar months or more have passed since it was submitted. "Six calendar months" is worked out as in F01 V7: the same Europe/London day and time six months on, or the last day of that month if it is shorter. A booking at exactly that moment is due. Bookings in every state are due alike. |
| P3 | A run erases every due booking (E1), recording the time of the run as the time of erasure. |
| P4 | **Network addresses.** The network address is kept for 7 days only. A run also empties the network address of every booking, erased or not, that was submitted 7 days (168 hours of elapsed time) or more ago. Exactly 7 days is included. Nothing else about such a booking changes. |
| P5 | A run changes nothing else: never a state, a date, the auto-declined mark, or any detail of a booking that is not due. |
| P6 | **Heartbeat.** A run that succeeds exits with code 0, writes "Purge run: N erased, M addresses removed." to the logger `app.jobs` at level INFO, and prints the same line. N is the number of bookings this run erased and M the number of other bookings whose network address it removed (P4); a booking erased by this run counts in N only. Either may be 0. The line holds no client details. |
| P7 | A run that fails exits with code 1, changes nothing, and writes and prints "Purge run failed: <type of the error>." at level ERROR, with the error's own message left out (F01 P1). |
| P8 | **Last run.** Every successful run records its instant, in the same all-or-nothing step as its erasures; a failed run records nothing; the recorded time never moves backwards (as F03 R5). `GET /health` gains `purge_last_run`, in the form and under the rules of F03 R6 and R7, next to `auto_decline_last_run`. |
| P9 | **Running again changes nothing** (E5), and a run that stops part-way leaves nothing changed; the next run does the work. |
| P10 | **Missed runs.** The first run after a gap erases everything due by then, with that run's time. |
| P11 | **Overlapping runs.** If two purge runs overlap, every due booking is erased exactly once and the numbers they report add up. |
| P12 | **With the auto-decline job.** A purge run and an auto-decline run at the same instant never wait for each other and never block each other: each skips a booking the other holds at that moment and leaves it for its own next run. Afterwards every booking that was overdue is declined and every booking that was due is erased, within one further run of each job. |
| P13 | **With an admin.** A booking another request holds at that moment is skipped and left for the next run (as F03 J10). |
| P14 | A run writes nothing to `app.email`. |

## Admin page (React)

| # | Rule |
|---|---|
| W1 | An erased booking's row shows "Deleted" in the Name column and nothing in the Email, Phone, Guests and Details columns. Its other columns and its action buttons are as for any booking in that state. |
| W2 | Below the table is a section headed "Delete client data", with a select labelled "Booking" and a button "Delete data". The select lists every booking on the page that is not erased, as "<name>, <start as YYYY-MM-DD HH:MM>", after a first empty choice "Choose a booking". The button is disabled until a booking is chosen. With no such booking on the page, the section shows "No client data on this page." in place of the select and button. |
| W3 | "Delete data" opens a dialog "Delete this client's data? This cannot be undone." with buttons "Yes, delete" and "Cancel". Only "Yes, delete" sends the request of D1, with `"confirm": true`. "Cancel" sends nothing. |
| W4 | On `200` the row shows the erased booking (W1) and the select no longer lists it. On `409` the page shows "This booking is still live. Decline it first, or wait until the event is over." On `404` or anything else, "Something went wrong. Please try again later." A `401` returns to the login form (F02 W10). |

## The terms and the privacy notice

Two separate documents, each a page of the public site, linked from the booking form.

| # | Rule |
|---|---|
| T1 | The page at `/terms` has the heading "Terms and conditions" and the page at `/privacy` the heading "Data and privacy notice". Each shows "Last updated: <date>". |
| T2 | On the booking form, each tick has a link to its document next to it, "Read the terms and conditions" and "Read the data and privacy notice", opening in a new tab. The tick labels themselves are unchanged (F01 U1). |
| T3 | The privacy notice states, each under its own heading: **who we are** (the centre's name, address and contact details); **what we collect** (name, email, phone, number of guests, date and times, event details, and the network address of the device); **why, and our legal basis** (handling the request: steps taken at the client's request before entering a contract; the network address: our legitimate interest in protecting the form from abuse); **how long we keep it** (six months from the day the request is submitted, then deleted automatically, leaving only the date and the outcome; the network address for 7 days); **who sees it** (the management team and the company hosting the website); **your rights** (to a copy, to correction, to deletion, to restrict or object); **how to ask** (by phone or email, free of charge, answered within one month); **how to complain** (to the Information Commissioner's Office, ico.org.uk, 0303 123 1113). |
| T4 | The terms state: a request is not a booking until the centre accepts it; the price and details are agreed by phone; one event per day, at most 12 hours, requested at most six months ahead; at most two requests at a time per person; **a request the centre has not answered within 48 hours lapses and its date is released, without further notice**; and that the centre may decline a request. |
| T5 | The centre's name, address, phone and email appear in both documents and come from one place in the code. Until the author supplies them they are the placeholders "[Centre name]", "[Centre address]", "[Centre phone]" and "[Centre email]". |

## Database

- The constraint that a booking is either complete or erased (data-model.md) no longer requires the network address of a booking that is not erased, since P4 empties it after 7 days.
- `job_runs` gains a row for the purge (P8).
- As in F03, `flask --app app init-db` makes the change to an existing table without changing existing data.

## Known limits

- **The application log is not purged.** Client details written to the log by the logged emails (F01 E1, E2; F02 ST7) are not removed by an admin's deletion or by the purge. Until real email sending replaces the logged emails, whoever keeps the logs must delete them within the same six months.
- **The centre's details in the two documents are placeholders** (T5). The documents must not go live until the real details are in, and the text has not been checked by a lawyer.
- **Which version of the terms a client agreed to is not recorded**; only the time of the tick, which is itself erased with the booking.
- **A purge can erase an accepted booking whose event is still to come**, if the event is six months after the request (R1, decision 21). The booking keeps its day; the team no longer has the client's details.
- **Nothing schedules the purge and nothing raises an alarm if it stops**, exactly as for F03's job; the heartbeat and `/health` make it visible.
- **The delete control is a section below the table, not a button in each row** (W2), so that the tracked F02 and F03 page tests, which fix each row's buttons and the table's columns, stay as they are.

## Where this differs from other documents

| Document says | F04 does |
|---|---|
| F01 S3: the network address "is erased when the booking is erased" | It is also emptied on its own after 7 days (P4). |
| `data-model.md`: a booking that is not erased has a network address | Not after 7 days (Database). `data-model.md` is updated with this feature. |
| FR18 and R1 decision 22: admins can delete a client's data | Only once the booking is declined or its event is over (D4), decided by the author on 2026-10-13. |
| F03 R6: `/health` returns `status` and `auto_decline_last_run` | It also returns `purge_last_run` (P8). Tracked tests that compare the whole `/health` body must be changed. |
| NFR7: data "kept for 6 months ... and is then removed automatically" | Removed by a command that a scheduler must run (P1); see Known limits. |

## Confirmed by the author

On 2026-10-13 the author accepted the implementer's proposals as defaults: the split of E1; the 7-day life of the network address (P4); erased bookings staying visible with no added field (A1); deletion only when a booking is no longer live (D4); the two legal bases (T3); the 48-hour sentence in the terms (T4); state changes on erased bookings (A3); the endpoint, its confirmation and its answers (D1 to D9); the purge command and its hourly schedule (P1 to P14); and the Known limits.

## Proposed by the implementer, not yet confirmed by the author

- The delete control as a section below the table (W2), chosen to avoid changing tracked page tests. The alternative is a "Delete data" button in each row, which needs about eight tracked F02 and F03 page tests changed.
- The wording of the page (W1 to W4), of the log lines (D8, P6, P7), and the name `purge_last_run`.
- The placeholders for the centre's details (T5), and "Last updated" dates on the two documents.
- Where erased bookings fall when sorting by name (A2).
