# Spec F01: public booking form with API

A member of the public fills in a booking request form. The form posts to the API, which checks the request, stores it as a booking in state `submitted`, and logs the two emails that will later be sent.

- **Sources:** `docs/requirements.md` (FR5, FR10, FR13 to FR17, NFR3), `docs/design/data-model.md`, `docs/design/application-state-machine.md`, the author's rules and answers of 2026-10-13, including the decisions on the hostile-input review.
- **Rule numbers** (V1, L2, ...) are cited by the tests.

## Out of scope

Admin page and admin actions, state changes after creation, the 48-hour auto-decline job, erasure and the 6-month removal, really sending email, a real CAPTCHA provider.

## API

`POST /api/v1/bookings`, JSON request body, JSON response.

### Request fields

| Field | JSON type | Required | Rule |
|---|---|---|---|
| `name` | string | yes | V1 |
| `email` | string | yes | V2 |
| `phone` | string | yes | V3 |
| `guest_count` | integer | yes | V4 |
| `starts_at` | string | yes | V5 to V7 |
| `ends_at` | string | yes | V5, V8, V9 |
| `details` | string | no | V10 |
| `terms_accepted` | boolean | yes | V11 |
| `privacy_notice_accepted` | boolean | yes | V11 |
| `captcha_token` | string | yes | V12 |

Fields not in this table are ignored.

### Responses

| # | Case | Status | Body |
|---|---|---|---|
| A1 | Booking created | `201` | `{"id": <integer>, "state": "submitted", "starts_at": "<as sent>", "ends_at": "<as sent>"}` |
| A2 | Content type is not `application/json` (B1) | `415` | `{"error": "unsupported_media_type"}` |
| A3 | Body larger than 64 KB (B2) | `413` | `{"error": "request_entity_too_large"}` |
| A4 | Body cannot be read as one JSON object (B3) | `400` | `{"error": "invalid_request"}` |
| A5 | One or more fields fail V1 to V12 | `400` | `{"error": "validation_failed", "fields": {"<field>": "<code>", ...}}` |
| A6 | CAPTCHA check fails (C1) | `403` | `{"error": "captcha_failed"}` |
| A7 | Rate limit reached (L1) | `429` | `{"error": "rate_limited", "message": "Too many responses submitted. Try again later."}` |
| A8 | Slot limit reached (L2) or day already taken (L3) | `409` | `{"error": "not_accepted"}` |
| A9 | Unknown address under the application | `404` | `{"error": "not_found"}` |
| A10 | Method other than `POST` on `/api/v1/bookings`, including `OPTIONS` and `HEAD` | `405` | `{"error": "method_not_allowed"}` (no body for `HEAD`) |
| A11 | Unexpected failure inside the application | `500` | `{"error": "internal_server_error"}` |

Every response has content type `application/json`.

**G1. Generic refusals.** A response never contains the client's name, email, phone or details. No response says or implies whether a day is taken or whether a person already holds bookings: A8 is the same body for both reasons, and it carries no date and no message.

### Order of checks

**O1.** The checks run in the order A10, A2, A3, A4, A5, A6, A7, A8, and the first failure is returned. No booking is stored unless every check passes.

## Reading the body

| # | Rule |
|---|---|
| B1 | Only the content type `application/json` is accepted, with or without a `charset` parameter. Anything else, or no content type, is refused (A2). |
| B2 | A body larger than 64 KB (65,536 bytes) is refused (A3). |
| B3 | The body must be one JSON object in UTF-8. It is refused (A4) if it is not valid JSON, is not an object, contains `NaN` or `Infinity`, contains a number written with an exponent (such as `1e2`), contains the same key twice in one object, or is nested more than 10 levels deep. The outer object is level 1. |

## Validation rules

"Now" is the current time. All times are Europe/London local times. Lengths are counted in Unicode code points.

**Trimming.** `name`, `email` and `phone` have leading and trailing whitespace removed before they are checked and stored. `details` is not trimmed.

**Control characters** are the Unicode control characters (category Cc, which includes tab, line feed, carriage return and NUL) and unpaired surrogates.

| # | Field | Rule | Code when broken |
|---|---|---|---|
| V1 | `name` | After trimming, 1 to 100 characters with no control characters | missing, not a string, or empty after trimming: `required`; over 100: `too_long`; control character: `invalid` |
| V2 | `email` | After trimming, at most 254 characters, with exactly one `@`, at least one character before it, a domain after it that contains a `.` and neither starts nor ends with one, no whitespace and no control characters | missing, not a string, or empty after trimming: `required`; over 254: `too_long`; otherwise: `invalid` |
| V3 | `phone` | After trimming, at most 30 characters, made only of the ASCII digits `0` to `9`, `+`, spaces and dashes (`-`), containing 7 to 15 digits | missing, not a string, or empty after trimming: `required`; over 30: `too_long`; otherwise: `invalid` |
| V4 | `guest_count` | A whole number from 1 to 250, sent as a JSON integer of any length. Strings, decimals and booleans are refused | missing: `required`; not a JSON integer: `invalid`; below 1 or above 250: `out_of_range` |
| V5 | `starts_at`, `ends_at` | A string of the form `YYYY-MM-DDTHH:MM` in ASCII digits, naming a date and time that exists in Europe/London. Year `0000`, impossible dates such as 30 February, and the hour skipped when the clocks go forward are refused. A time in the hour repeated when the clocks go back means its first occurrence | missing: `required`; anything else: `invalid` |
| V6 | `starts_at` | Later than now. A start equal to now is refused | `in_past` |
| V7 | `starts_at` | No later than six calendar months after now, at the same local time of day. If that day does not exist in the target month, the last day of that month is used | `too_far_ahead` |
| V8 | `ends_at` | At least 1 hour of elapsed time after `starts_at`. This also refuses an end at or before the start | `duration_too_short` |
| V9 | `ends_at` | At most 12 hours of elapsed time after `starts_at` | `duration_too_long` |
| V10 | `details` | Optional. If present and not `null`, a string of at most 2000 characters whose only permitted control character is the line feed. An empty string is treated as absent | not a string, or a control character other than line feed: `invalid`; over 2000: `too_long` |
| V11 | `terms_accepted`, `privacy_notice_accepted` | Each must be the JSON value `true` | `required` |
| V12 | `captcha_token` | A non-empty string of at most 2048 characters | missing, not a string or empty: `required`; over 2048: `too_long` |
| V13 | all | Every field that fails is reported in the same response, one code per field. For a field that breaks several rules, the first code listed in its row is used. V6 and V7 are checked only when `starts_at` is well-formed; V8 and V9 only when both times are well-formed | |
| V14 | `starts_at`, `ends_at` | Any time of day is accepted; the centre is open 24 hours | |

## CAPTCHA

| # | Rule |
|---|---|
| C1 | The `captcha_token` and the client's network address are passed to the CAPTCHA verifier. If the verifier does not pass them, the request is refused (A6). |
| C2 | In F01 the verifier is a stand-in, like the emails: it passes every token and writes one line to the logger `app.captcha` at level INFO. The line reads "CAPTCHA stand-in passed a token." and contains neither the token nor the network address. No CAPTCHA provider is contacted. |

## Limits

| # | Rule |
|---|---|
| L1 | **Rate limit.** If 5 or more bookings were created from the same network address less than 24 hours before now, the request is refused (A7). A booking created exactly 24 hours ago no longer counts. Bookings in every state count. For IPv6, every address in the same /64 block counts as one network address; an IPv4 address counts by itself. An IPv4 address written in IPv6 form (`::ffff:a.b.c.d`) is that IPv4 address, and is stored as such. |
| L2 | **Slot limit.** A person may hold at most 2 active slots. An active slot is a booking that is not declined and whose end is later than now. A booking belongs to the same person if its email matches ignoring letter case, **or** its phone matches after normalising: spaces and dashes are removed, then a leading `+44` is replaced by `0`. If the person already holds 2, the request is refused (A8). |
| L3 | **Day lock.** At most one non-declined booking per calendar day, in Europe/London time. A booking locks every calendar day from its start to its end; one that ends exactly at midnight does not lock the following day. If any day of the request is locked by another non-declined booking, the request is refused (A8). A declined booking locks nothing. |
| L4 | **Double submit.** There is no separate rule. A repeated submission asks for a day the first one already locked, so it is refused by L3 (A8). |
| L5 | **Simultaneous requests.** L1, L2 and L3 hold when requests arrive at the same instant: of two simultaneous requests for the same day exactly one is created, and simultaneous requests cannot take a network address past 5 or a person past 2. |
| L6 | **Network address.** The client's network address is the address of the connection. Forwarded-address headers sent by the client are ignored. Only when the application is told how many trusted proxies sit in front of it (`TRUSTED_PROXY_HOPS`, set by the hosting platform) is the address taken from the `X-Forwarded-For` header, counting that many entries from the right. If the header is missing, has fewer entries than that, or that entry is not a network address, the address of the connection is used. |

## Storage

| # | Rule |
|---|---|
| S1 | A created booking has state `submitted`, the submission time, the two tick times, and the client's network address. Start and end are stored in UTC. |
| S2 | `name`, `email`, `phone` (after trimming) and `details` are stored exactly as sent. Nothing is HTML-escaped or stripped on the way in. |
| S3 | The network address is one of the client details: it is erased when the booking is erased. |
| S4 | The API produces JSON only and never HTML. Escaping happens wherever user text is put into a page: in F01 that is the form's confirmation (U5). The admin page feature must prove its own escaping. |

## Emails

Emails are logged, not sent.

| # | Rule |
|---|---|
| E1 | When a booking is created, a **client confirmation** is written to the logger `app.email` at level INFO. It contains the recipient (the client's email), the client's name, and the start and end of the booking in the form of V5. |
| E2 | When a booking is created, a **team notification** is written to the same logger. Its recipient is the address in the `TEAM_EMAIL` setting, and it contains the client's name, email, phone, guest count, start and end in the form of V5, and details. |
| E3 | Nothing is written to `app.email` when a request is refused. |
| E4 | The running application writes the INFO lines of `app.email` and `app.captcha` to its log output (standard error), without any extra logging set-up. |

## Log safety

| # | Rule |
|---|---|
| P1 | Client text never shapes the log, and error text never reaches it. **(a)** When the application fails unexpectedly (A11), it writes one line to the log holding only the type of the error and, if a booking had already been stored, that booking's ID. The error's own message is never logged, because database errors can quote the client's details. **(b)** Every client-supplied value written to the logs, including the logged emails of E1 and E2, has its line breaks collapsed: each run of line-break characters (line feed, carriage return, vertical tab, form feed, next line U+0085, line separator U+2028, paragraph separator U+2029) becomes one space. What is stored is unchanged (S2). |

## Form (React)

A booking request page containing the form.

| # | Rule |
|---|---|
| U1 | The form has inputs labelled "Name", "Email", "Phone", "Number of guests", "Start", "End" and "Additional details", a tick labelled "I agree to the terms and conditions", a separate tick labelled "I have read the data and privacy notice", the CAPTCHA widget, and a button "Send booking request". Start and End are date-and-time inputs, whose values have the form of V5. |
| U2 | Inputs carry the limits from V1 to V4 and V10: maximum lengths 100, 254, 30 and 2000, and guests from 1 to 250 in steps of 1. |
| U3 | The submit button is disabled until both ticks are set and the CAPTCHA has produced a token. |
| U4 | Submitting sends one `POST /api/v1/bookings` with content type `application/json` and the fields of the request table as JSON. `guest_count` is sent as a number. The button is disabled while the request is in flight. |
| U5 | On `201` the form is replaced by the confirmation "Thank you, <name>. Your booking request has been sent." The name is shown as text; any markup in it is not interpreted. |
| U6 | On any other response the form stays filled in and shows a message (table below). |
| U7 | In F01 the CAPTCHA widget is a stand-in: a tick labelled "I am not a robot" that produces the token `stand-in-token` when ticked and no token when unticked. |

### Messages

| Response | Shown |
|---|---|
| `400` with `fields` | next to each field, including the two ticks and the CAPTCHA widget, by code: `required` "This field is required."; `too_long` "This is too long."; `invalid` "This is not valid."; `out_of_range` "Guests must be between 1 and 250."; `in_past` "The start must be in the future."; `too_far_ahead` "Bookings can be made at most 6 months ahead."; `duration_too_short` "A booking must be at least 1 hour."; `duration_too_long` "A booking can be at most 12 hours." |
| `409` | "We could not accept this booking request. Please contact the centre." |
| `429` | "Too many responses submitted. Try again later." |
| `403` | "The CAPTCHA check failed. Please try again." |
| `400` with `fields` that names no field of the form, or names none at all | "Something went wrong. Please try again later." |
| anything else, or no response | "Something went wrong. Please try again later." |

The messages for `400` describe only the client's own input. No message mentions whether a day is available (G1).

## Replaceable parts

The form takes its CAPTCHA widget as a replaceable component, `CaptchaWidget`, which is given a function `onToken` to call with the token. The default is the stand-in of U7.

Two parts of the backend can be replaced through its configuration, so that tests control them:

| Key | What it is | Default |
|---|---|---|
| `CLOCK` | a function returning "now" as a Europe/London local date and time. Since F02 it may instead return a time carrying its own time zone, taken as that exact instant, which is what the real clock does (F02 CK1, CK2) | the real clock |
| `CAPTCHA_VERIFIER` | a function taking the token and the client's network address and returning whether the check passed | the stand-in of C2 |

## Tooling

`make test` runs the backend tests and then the frontend tests (`npm test`, Vitest with Testing Library). The CI `test` job therefore runs both.

## Database

Access is plain SQL through the repositories; there is no ORM. The schema is the `bookings` table of `docs/design/data-model.md`, kept in `backend/db/schema.sql`. The command `flask --app app init-db` creates it in the database named by `DATABASE_URL`, and does nothing to tables that already exist.

## Known limits

Parked or accepted by the author on 2026-10-13.

- **CAPTCHA is a stand-in.** F01 has no real CAPTCHA provider (C2, U7), so the form is not protected against automated submissions beyond the rate limit. Cloudflare Turnstile was chosen as the provider and is left for a later feature, together with tests for a replayed token.
- **Calendar blocking by many identities is an accepted risk.** One actor using a new name, email and phone each time can lock up to 10 days per network address per day (five 12-hour bookings across midnight), and nothing in F01 releases those locks.
- **Slow request bodies and cross-origin requests are not handled by the application.** The form and the API are served from the same origin, and the hosting platform (Azure) is relied on for connection handling.
- **The slot limit is easy to sidestep.** A different email and a different phone make a different person (L2).

## Proposed by the implementer, approved by the author

All of the following were approved by the author on 2026-10-13.

- The error names in the response bodies, and `request_entity_too_large` and `unsupported_media_type` for A2 and A3.
- Unpaired surrogates treated as control characters. Zero-width and text-direction characters are **not** control characters, so a name made only of zero-width spaces is accepted.
- A carriage return in `details` is refused (V10 allows line feed only), so text with Windows line endings is refused unless the sender converts it. Browsers send line feeds from a text area.
- A `+` is allowed anywhere in the phone (V3), not only at the start. Only a leading `+44` is normalised (L2); `0044` is not.
- Whitespace at the very start or end of an email is trimmed, so a trailing line break is removed, not refused. A line break inside the email is refused.
- The email rule (V2) and 7 to 15 digits in a phone (V3).
- Decimals such as `2.0` are refused for `guest_count` (V4), as a field error; an exponent anywhere in the body is refused as an unreadable body (B3).
- Booking length is elapsed time (V8, V9), which follows from storing UTC: on the night the clocks go forward, 00:30 to 02:30 on the clock is 1 hour.
- "6 months" measured in calendar months on the local start time (V7); no minimum notice period.
- The rate limit counts created bookings only; refused submissions do not count (L1).
- The team notification is logged like the client confirmation (E2).
- `TRUSTED_PROXY_HOPS` as the way the platform tells the application to trust `X-Forwarded-For` (L6).
- The wording of every message shown by the form.
